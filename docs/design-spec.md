# eastx — 設計仕様書

> **個人のレジュメ／ポートフォリオサイト eastasian を、「自作CMS＋フロント」の構成のまま作り直し、ブログやコーディング記録も載せられる場所にする。**

入力: `docs/concept.md`（Phase 0）、`docs/brainstorm-notes.md`（Phase 1）
画面遷移図: `docs/screen_flow.mermaid`（別紙）

---

## 1. プロダクト概要

### 1.1 コンセプト

今のサイト eastasian（https://eastasian.vercel.app/）は、日英を切り替えられる1ページのレジュメで、自作のCMS（管理画面＋API）で中身を更新している。
これを次の4つの課題を解消する形で作り直す。

| 今の課題 | 作り直しで目指すこと |
|---|---|
| 技術が古く、保守がつらい | 手を入れやすい構成にする（技術スタックは Phase 3 で決める） |
| CMSでの更新が面倒 | 自作CMSを、更新しやすさを重視して作り直す |
| 見せ方・デザインが今の自分に合っていない | 見せ方を刷新し、見た目はあとから差し替えられるようにする |
| 載せたい中身を載せる場所がない | ブログとコーディング記録を新しく載せる |

訪問者（採用担当・リクルーター、フリーランスの依頼主、エンジニア仲間）には、次の体験を届ける。

- トップを見てすぐに、何ができる人で、どんな経歴かがわかる
- 作品・プロジェクトを掘り下げて実力を確かめられ、信頼できる
- ブログやコーディング記録から、考え方や興味といった人となりが伝わる
- すべての中身を日本語と英語の両方で読める

持ち主（管理者）にとっては、経歴や学びを積み上げていく自分の記録の場所であり、サイト自体も技術力を示す作品になる。

### 1.2 プロダクト方針

| 項目 | 方針 |
|---|---|
| 用途 | ポートフォリオ（マネタイズなし）。サイト自体も作品として見せる |
| スコープ | フル機能を一度に公開する。レジュメ・作品・プロジェクト・ブログ・コーディング記録・自作CMSをすべてそろえてから公開する |
| 構成 | 「公開サイト（フロント）」と「管理画面（CMS）」に分ける。CMSは自作する |
| 対応言語（公開側） | 日本語と英語の2言語（i18nあり）。URLを `/ja` と `/en` で分ける。詳細は 1.4 |
| 対応言語（管理側） | 日本語のみ（使うのは持ち主1人のため）。入力する中身は日英の両方 |
| 対応デバイス（公開側） | スマホとPCの両方。どの画面幅でも同じ1列のレイアウトにする |
| 対応デバイス（管理側） | PC優先。スマホでも崩れずに使える程度に対応する |
| データ移行 | 今の公開サイトから中身を抽出し、新しいデータ構造に移す（9章） |

### 1.3 UI設計原則

| 原則 | 内容 |
|---|---|
| 1ページで伝わる | 公開側は、トップの1ページだけで何者かがわかるようにする。レジュメ・作品・プロジェクト・ブログ・コーディング記録の一覧は、独立した画面にせず、トップのセクションとして持つ |
| 移るのは詳細だけ | 別ページに移るのは、詳細（作品詳細、プロジェクト詳細、ブログ記事、コーディング記録詳細）を見るときだけ。それ以外の操作（セクション間の移動、続きを見る、言語やテーマの切り替え）ではページを移らない |
| セクション内ページング | 件数が多いセクションは、項目を縦に5件まで積んで1ページとし、次の5件へは横にページングする。ページ（URL）は移らない（6.1.3） |
| 詳細は任意 | 作品・プロジェクトは、詳細本文を書いたものだけが詳細ページを持つ。詳細のないものは、外部リンクやGitHubへ直接進む |
| 見た目は差し替えられるように | 装飾は最小限にし、色・文字・角丸・余白などの見た目はすべてデザイントークン経由で指定する。あとからトーンを変えるときは、トークンの差し替えで済むようにする |
| 日英は同じ扱い | どの画面も、日本語と英語で同じ構成・同じ情報量で見せる。片方の言語しかない中身は、もう片方の言語で出して注記する |
| 管理画面は一覧性 | 管理画面は持ち主しか使わないので、余白より一覧性と操作の速さを優先する |

### 1.4 言語（i18n）の仕様

| 項目 | 仕様 |
|---|---|
| URL | すべての公開ページを `/ja/...` と `/en/...` の2系統で持つ。例: `/ja/works/my-app` と `/en/works/my-app`。スラッグ（URLの末尾）は日英で共通 |
| ルート `/` を開いたとき | 以前に選んだ言語があればその言語へ、なければブラウザの言語が日本語なら `/ja`、それ以外は `/en` へリダイレクトする |
| 言語の切り替え | ヘッダーの「JA ／ EN」で切り替える。今いる画面のまま、URLの言語の部分だけを変えて開き直す。選んだ言語は覚えておき、次回のルート `/` の振り分けに使う |
| 片方の言語しかない中身 | もう片方の言語の本文を出し、「この記事は日本語のみです」／「This post is available in Japanese only.」のような注記を添える。トップのカードにも「日本語のみ」「English only」の小さなラベルを付ける |
| 言語ありの判定 | 中身ごとに、必須のテキスト（タイトル。本文を持つ種類は本文も）がその言語で入っていれば「その言語あり」とする。7章の各テーブルの備考を参照 |
| UIの文言 | ボタン・見出し・注記などの固定文言は、日英の辞書で持つ |
| 日付の表記 | 日本語: `2026年9月`、`2026年9月12日`。英語: `Sep 2026`、`Sep 12, 2026` |

## 2. ユーザーロールとフロー

### 2.1 ロール定義

| ロール | 概要 | 主な操作 |
|---|---|---|
| 訪問者 | 採用担当・リクルーター、フリーランスの依頼主、エンジニア仲間など、サイトを見に来る人。ログインしない | 公開側の全画面の閲覧。セクション内ページング、詳細ページの閲覧、外部リンク・GitHubを開く、言語とテーマの切り替え |
| 管理者 | サイトの持ち主（自分）1人。GitHubアカウントでCMSにログインする | すべての中身（プロフィール、経歴、作品、プロジェクト、使用技術、ブログ、コーディング記録）の作成・編集・下書き保存・公開・非公開化・削除、並べ替え、画像のアップロード |

### 2.2 フロー全体像

```
訪問者（コアフロー「何者かつかみ、作品で確かめる」）:
  トップを開く → プロフィールと経歴で要点をつかむ
  → 同じページの作品欄・プロジェクト欄をセクション内でページングして見る
  → 作品詳細／プロジェクト詳細（背景・工夫・使用技術・画像）
  → 外部リンクやGitHubで実物を確かめる（別タブ）
  ※ 詳細のない作品・プロジェクトは、トップのカードから外部リンク・GitHubへ直接進む

訪問者（人となりを知る）:
  トップのブログ欄／コーディング記録欄をページングして見る → ブログ記事／コーディング記録詳細を読む → トップの該当セクションへ戻る

管理者（書いて公開する）:
  管理画面のURLを開く → GitHubでログイン → ダッシュボード
  → 各管理画面の一覧 → 新規作成または編集 → 下書き保存 → プレビューで確認 → 公開
  → 公開サイトで確認
```

### 3.2 訪問者面（公開側）

### 3.3 管理者面（管理画面・CMS）

| # | 画面名 | URL例 | 目的 | レイアウト | 認証 | 説明 |
|---|---|---|---|---|---|---|
| A1 | ログイン | `/admin/login` | 管理者だけが入る | L3 中央カード | 不要 | 「GitHubでログイン」ボタンだけを置く。管理者として登録したGitHubアカウントだけを通す |
| A2 | ダッシュボード | `/admin` | 管理作業の起点 | L4 サイドメニュー＋一覧 | 必要 | 種類ごとの件数（公開／下書き）、下書きの一覧、新規作成の近道、公開サイトへのリンク |
| A3 | プロフィール編集 | `/admin/profile` | プロフィールを更新する | L6 サイドメニュー＋フォーム | 必要 | 名前・肩書き・写真・自己紹介・SNSリンク。1件だけなので一覧ビューは持たない |
| A4 | 経歴管理 | `/admin/careers`、`/admin/careers/{id}` | 経歴を更新する | 一覧: L4、編集: L6 | 必要 | 職歴・学歴の一覧（期間の新しい順、種類で絞り込み）と編集 |
| A5 | 作品管理 | `/admin/works`、`/admin/works/{id}` | 作品を更新する | 一覧: L4、編集: L5 | 必要 | 一覧（表示順の並べ替え）と編集（詳細本文・画像を含む） |
| A6 | プロジェクト管理 | `/admin/projects`、`/admin/projects/{id}` | プロジェクトを更新する | 一覧: L4、編集: L5 | 必要 | 一覧（表示順の並べ替え）と編集（詳細本文・画像を含む） |
| A7 | 使用技術管理 | `/admin/stacks`、`/admin/stacks/{id}` | 技術スタックを更新する | 一覧: L4、編集: L6 | 必要 | 一覧（表示順の並べ替え）と編集（名前・アイコン・リンク・トップに表示するか） |
| A8 | ブログ管理 | `/admin/blog`、`/admin/blog/{id}` | 記事を書いて公開する | 一覧: L4、編集: L5 | 必要 | 一覧（公開日の新しい順、状態で絞り込み）と、Markdownエディタ・プレビュー・公開 |
| A9 | コーディング記録管理 | `/admin/coding`、`/admin/coding/{id}` | 記録を書いて公開する | 一覧: L4、編集: L5 | 必要 | 一覧（公開日の新しい順、状態・種類で絞り込み）と、Markdownエディタ・プレビュー・公開 |

- 新規作成は、各一覧ビューの「新規作成」から、空の編集ビュー（URL例: `/admin/works/new`）を開く。
- 公開サイトには、管理画面への入口を置かない。管理画面はURLを直接開いて入る。
- 管理画面は検索エンジンに載せない（クロールさせない）。

## 4. デザインシステム

### 4.1 レイアウトパターン定義

| パターン | 名前 | 使う場面 | 構造 |
|---|---|---|---|
| L1 | シングルカラム・ロングページ | 1ページで全体を伝える画面 | 上部に固定ヘッダー、その下に読みやすい幅の1列で、セクションを縦に積む。画面幅が広くても1列のまま中央に置く。セクションごとにページングできる |
| L2 | 記事カラム | 1つの中身に集中して読ませる画面 | L1と同じヘッダーと、同じ幅の1列。上から「戻るリンク → タイトルとメタ情報 → 画像 → 本文 → 前後のナビ」の順 |
| L3 | 中央カード | 1つの操作だけをさせる画面 | 画面中央に小さなカードを1枚置く。ヘッダーやメニューはない |
| L4 | サイドメニュー＋一覧 | 管理画面で、たくさんの中身を見渡して選ぶ画面 | 左に固定のサイドメニュー、右に上部の操作バー（新規作成・絞り込み）とテーブル |
| L5 | サイドメニュー＋2ペイン編集 | 管理画面で、長い本文を書いて確かめる画面 | 左にサイドメニュー、右の上部に操作バーと基本項目、その下を左右に分けて「Markdownエディタ ／ プレビュー」 |
| L6 | サイドメニュー＋フォーム | 管理画面で、短い項目を入力する画面 | 左にサイドメニュー、右に1列のフォーム。Markdownの欄は、ボタンで入力とプレビューを切り替える |

| # | 画面 | パターン | スクロール | 根拠 |

### 4.3 レスポンシブ方針

| ブレイクポイント | 幅 | 公開側（L1・L2） | 管理側（L3〜L6） |
|---|---|---|---|
| デスクトップ | ≥1024px | 1列のまま中央に置く。ヘッダーにメニューを横並びで出す。ページングは ◀ ▶ ボタン（キーボードの ← → も可） | サイドメニューを常に表示。L5はエディタとプレビューを左右に並べる |
| タブレット | 768〜1023px | 1列。ヘッダーのメニューは横並びのまま（入りきらなければメニューボタンにまとめる）。ページングはボタンとスワイプの両方 | サイドメニューはアイコンだけに縮める。L5は左右に並べたまま |
| モバイル | <768px | 1列。ヘッダーのメニューはメニューボタンから開く。ページングは横スワイプが基本で、ボタンも残す | サイドメニューはメニューボタンから開く。L5はエディタとプレビューをタブで切り替える。テーブルは主要な列だけ残す |

### 4.4 ビジュアルデザイン方針

具体的な値（色コード・フォント名・サイズ・余白）は、Phase 3 で `docs/06_design-tokens.json` として決める。

| 項目 | 方針 |
|---|---|
| トーン&ムード | ミニマム。装飾は最小限にして、あとから変更できるようにしておく。見た目はすべてデザイントークン経由で指定し、コンポーネントに色や余白の値を直接書かない。トーンを変えるときはトークンの差し替えで済むようにする |
| カラーの方向性 | モノトーン（白・黒・グレー）を基調に、アクセント1色。アクセントは、リンク・ボタン・ページングの現在位置など、操作できる場所だけに使う |
| タイポグラフィの方向性 | 和文はゴシック体、英文はサンセリフ体。コードと日付・数値は等幅を使う。見出しと本文の差は、サイズと太さだけでつける |
| ライト/ダークモード | 両対応。初期状態はOSの設定に合わせる。ヘッダーに切り替え（OSに合わせる／ライト／ダーク）を置き、選んだ設定は覚えておく。公開側・管理側の両方で対応する |
| 情報密度 | 公開側はゆったり（余白を広めにとって読みやすく）。管理側は高密度（一覧性と操作の速さを優先） |
| 画像 | サムネイルは同じ縦横比で切り抜いて揃える（比率は Phase 3 でトークンとして決める）。画像がない中身は、画像の場所を空けずに詰める |
| 動き | ページングの切り替えは横にスライドする短いアニメーションだけにする。OSで「視差効果を減らす」が有効なら、アニメーションなしで切り替える |

## 6. コア画面詳細仕様

### 6.1 トップ（P1）

コアフローの起点で、公開側で最も重要な画面。

#### 6.1.1 レイアウト構造

```
┌──────────────────────────────────────────────┐
│ eastx      経歴 プロジェクト 作品 技術 ブログ 記録 │ ← 固定ヘッダー
│                              [JA|EN] [◐]      │
├──────────────────────────────────────────────┤
│            ┌───────────────────────┐          │
│            │  (写真)                 │          │
│            │  名前                   │          │ ← プロフィール
│            │  肩書き                 │          │
│            │  自己紹介               │          │
```

| 言語タブ（日本語／English） | 言語ごとの入力欄（タイトル・概要・本文など）を切り替える。共通の項目（スラッグ・リンク・使用技術・画像・日付など）はタブの外に置く。入力が済んでいない言語のタブに印を付ける |
| 下書き保存 | 入力を保存し、状態は下書きのまま（公開中のものを編集しているときは、このボタンの代わりに「非公開に戻す」を出す） |
| 公開する | 入力を保存して公開する。初めて公開するときは公開日を今の日時にする（ブログ・コーディング記録） |
| 更新する | 公開中のものを編集しているときに出す。保存すると公開サイトにも反映される |
| 非公開に戻す | 公開中のものを下書きに戻す。公開サイトから見えなくなる |
| 削除 | 確認ダイアログ「『△△アプリ』を削除します。元に戻せません」で「削除する」を押すと完全に消し、一覧ビューへ戻って「削除しました」と通知する |
| 画像のアップロード | サムネイル欄では、画像を選ぶかドラッグ＆ドロップする。Markdownエディタでは、画像を貼り付けるかドロップすると、アップロードして本文に画像の記法を入れる |
| プレビュー | L5では、Markdownを書くと右のプレビューにすぐ反映する（公開サイトと同じ見た目）。L6では、ボタンで入力とプレビューを切り替える |
| 一覧へ戻る・別の画面へ移る | 保存していない変更があれば「保存していない変更があります。移動しますか？」と確認する |

#### 6.7.2 画面ごとの入力項目

| 画面 | 言語ごとの項目（日英） | 共通の項目 |
|---|---|---|
| A3 プロフィール編集 | 名前、肩書き、自己紹介（Markdown） | 写真、SNSリンク（サービスを選んでURLを入れる。追加・削除・並べ替え） |
| A4 経歴管理 | タイトル、所属、場所、内容（Markdown） | 種類（職歴／学歴）、開始年月、終了年月（空なら「現在」） |
| A5 作品管理 | タイトル、概要、詳細本文（Markdown） | スラッグ、外部リンク、GitHub、使用技術、サムネイル |
| A6 プロジェクト管理 | タイトル、概要、詳細本文（Markdown） | スラッグ、開始年月、終了年月（空なら「現在」）、外部リンク、使用技術、サムネイル |
| A7 使用技術管理 | なし（技術名は固有名詞なので日英共通） | 識別名、表示名、アイコン画像、リンク、トップに表示するか |
| A8 ブログ管理 | タイトル、本文（Markdown） | スラッグ、サムネイル、公開日（公開後に変えられる） |
| A9 コーディング記録管理 | タイトル、本文（Markdown） | スラッグ、種類（学習ログ／コード断片／問題を解いた記録／技術メモ）、参考リンク、サムネイル、公開日（公開後に変えられる） |

- A3 プロフィール編集は1件だけなので、「保存」ボタンだけを置く（下書き・公開・削除はない）。
- A7 使用技術管理は下書き・公開を持たない。トップに出すかどうかは「トップに表示するか」で決める。削除するときは、使っている作品・プロジェクトの数を確認ダイアログに出し、削除するとそれらの紐づけも外れる。
- スラッグは、英語のタイトルから自動で作り、手で直せる。半角の英小文字・数字・ハイフンだけ。

#### 6.7.3 入力チェック

| 対象 | ルール | 出し方 |
|---|---|---|
| 下書き保存 | タイトルが日英のどちらかに入っていること（プロフィール・使用技術を除く） | 入力欄の下に赤字で理由を出し、保存しない |
| 公開する・更新する | 少なくとも1つの言語で「言語あり」になっていること（1.4）。スラッグが入っていること（作品・プロジェクト・ブログ・コーディング記録）。経歴は開始年月が入っていること。プロジェクトは開始年月が入っていること | 足りない項目を一覧で出し、該当する言語タブと入力欄に印を付ける |
| スラッグ | 形式が正しく、同じ種類の中で重複しないこと | 入力欄の下に理由を出す |
| 日付 | 終了年月は開始年月より後であること | 入力欄の下に理由を出す |
| URL | 外部リンク・GitHub・参考リンク・SNSリンクは `https://` で始まること | 入力欄の下に理由を出す |
| 画像 | 画像ファイルであること、大きさの上限内であること（上限は Phase 3 で決める） | アップロードを止め、理由を通知する |

#### 6.7.4 状態ごとの表示

| 状態 | 表示 |
|---|---|
| 新規作成 | 入力欄が空の編集ビュー。状態は「下書き（未保存）」 |
| 読み込み中 | 入力欄にスケルトン。保存・公開ボタンは無効 |
| 保存中 | ボタンを無効にし、押したボタンに読み込み中の印を出す |
| 保存に成功 | 「保存しました」「公開しました」などを短く通知する |
| 保存に失敗 | 「保存できませんでした。もう一度お試しください」と出し、入力した内容は消さない |
| 画像のアップロード中・失敗 | エディタに「アップロード中…」を出す。失敗したら仮の記法を消し、理由を通知する |
| 存在しないIDを開いた | 「見つかりませんでした」と「一覧へ戻る」 |

## 7. データモデル

論理設計。Phase 3 でORMのスキーマに変換し、所有権は System Design Doc に移る。

### 共通の約束

- すべてのテーブルに `id`（UUID、主キー）、`created_at`、`updated_at` を持たせる（以下の表では省略）。
- 日英を持つテキストは、`_ja` と `_en` の2つのカラムに分ける。どちらも空を許し、「言語あり」の判定（1.4）は各テーブルの備考のとおり。
- 公開状態 `status` は `draft`（下書き）か `published`（公開）。公開側には `published` だけを出す。
- 画像は、ストレージに置いたファイルのURLを持つ。本文中の画像は Markdown の中にURLとして入る。
- Markdown のカラムは、Markdown 記法のテキストをそのまま持つ。

### ER図

```
profile (1件)
social_link (N)                      ※ profile は1件だけなので外部キーは持たない

project N ──< project_stack >── N stack

blog_post (N)
coding_log (N)

admin_user (1件)
```
