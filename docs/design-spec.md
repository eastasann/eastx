# eastx — 設計仕様書

> **個人のレジュメ／ポートフォリオサイト eastasian を、「自作CMS＋フロント」の構成のまま作り直し、ブログやコーディング記録も載せられる場所にする。**

入力: `docs/concept.md`（Phase 0）、`docs/brainstorm-notes.md`（Phase 1）
画面遷移図: `docs/screen_flow.mermaid`（別紙）

## 1. プロダクト概要

### 1.1 コンセプト

今のサイト eastasian（https://eastasian.vercel.app/）は、日英を切り替えられる1ページのレジュメで、自作のCMS（管理画面＋API）で中身を更新している。
これを次の4つの課題を解消する形で作り直す。

| 今の課題 | 作り直しで目指すこと |
|---|---|
| 技術が古く、保守がつらい | 手を入れやすい構成にする（技術スタックは Phase 3 で決める） |
| CMSでの更新が面倒 | 自作CMSを、更新しやすさを重視して作り直す |
| 見せ方・デザインが今の自分に合っていない | 見せ方を刷新し、見た目はあとから差し替えられるようにする |
| 載せたい中身を載せる場所がない | ブログとコーディング記録を新しく載せる |

訪問者（採用担当・リクルーター、フリーランスの依頼主、エンジニア仲間）には、次の体験を届ける。

- トップを見てすぐに、何ができる人で、どんな経歴かがわかる
- 作品・プロジェクトを掘り下げて実力を確かめられ、信頼できる
- ブログやコーディング記録から、考え方や興味といった人となりが伝わる
- すべての中身を日本語と英語の両方で読める

持ち主（管理者）にとっては、経歴や学びを積み上げていく自分の記録の場所であり、サイト自体も技術力を示す作品になる。

### 1.2 プロダクト方針

| 項目 | 方針 |
|---|---|
| 用途 | ポートフォリオ（マネタイズなし）。サイト自体も作品として見せる |
| スコープ | フル機能を一度に公開する。レジュメ・作品・プロジェクト・ブログ・コーディング記録・自作CMSをすべてそろえてから公開する |
| 構成 | 「公開サイト（フロント）」と「管理画面（CMS）」に分ける。CMSは自作する |
| 対応言語（公開側） | 日本語と英語の2言語（i18nあり）。URLを `/ja` と `/en` で分ける。詳細は 1.4 |
| 対応言語（管理側） | 日本語のみ（使うのは持ち主1人のため）。入力する中身は日英の両方 |
| 対応デバイス（公開側） | スマホとPCの両方。どの画面幅でも同じ1列のレイアウトにする |
| 対応デバイス（管理側） | PC優先。スマホでも崩れずに使える程度に対応する |
| データ移行 | 今の公開サイトから中身を抽出し、新しいデータ構造に移す（9章） |

### 1.3 UI設計原則

| 原則 | 内容 |
|---|---|
| 1ページで伝わる | 公開側は、トップの1ページだけで何者かがわかるようにする。レジュメ・作品・プロジェクト・ブログ・コーディング記録の一覧は、独立した画面にせず、トップのセクションとして持つ |
| 移るのは詳細だけ | 別ページに移るのは、詳細（作品詳細、プロジェクト詳細、ブログ記事、コーディング記録詳細）を見るときだけ。それ以外の操作（セクション間の移動、セクションの次の5件を見る、経歴の「続きを読む」、テーマの切り替え）ではページを移らない。例外として、言語の切り替えは、同じ画面をもう一方の言語のURLで開き直す（1.4） |
| セクション内ページング | 件数が多いセクションは、項目を縦に5件まで積んで1ページとし、次の5件へは横にページングする。ページ（URL）は移らない（6.1.3） |
| 詳細は任意 | 作品・プロジェクトは、詳細本文を書いたものだけが詳細ページを持つ。詳細のないものは、外部リンクやGitHubへ直接進む |
| 見た目は差し替えられるように | 装飾は最小限にし、色・文字・角丸・余白などの見た目はすべてデザイントークン経由で指定する。あとからトーンを変えるときは、トークンの差し替えで済むようにする |
| 日英は同じ扱い | どの画面も、日本語と英語で同じ構成・同じ情報量で見せる。片方の言語しかない中身は、もう片方の言語で出して注記する |
| 管理画面は一覧性 | 管理画面は持ち主しか使わないので、余白より一覧性と操作の速さを優先する |

### 1.4 言語（i18n）の仕様

| 項目 | 仕様 |
|---|---|
| URL | すべての公開ページを `/ja/...` と `/en/...` の2系統で持つ。例: `/ja/works/my-app` と `/en/works/my-app`。スラッグ（URLの末尾）は日英で共通 |
| ルート `/` を開いたとき | 以前に選んだ言語があればその言語へ、なければブラウザの言語が日本語なら `/ja`、それ以外は `/en` へリダイレクトする |
| 言語の切り替え | ヘッダーの「JA ｜ EN」で切り替える。同じ画面を、URLの言語の部分だけを変えて開き直す。トップでは見ていたセクションのスクロール位置を保ち、各セクションのページングは1ページ目に戻る。選んだ言語は覚えておき、次回のルート `/` の振り分けに使う |
| 言語ありの判定 | 中身ごとに、その言語で「言語あり」かを判定する。ブログ・コーディング記録はタイトルと本文の両方、プロフィールは名前、それ以外（経歴・作品・プロジェクト）はタイトルが入っていれば「言語あり」。7章の各テーブルの備考にも書く |
| 片方の言語しかない中身 | 表示中の言語で「言語あり」でない中身は、もう片方の言語で出し、「この記事は日本語のみです」／「This post is available in Japanese only.」のような注記を添える。トップのカード・行にも小さな言語ラベルを付ける（/ja で英語だけの中身には「英語のみ」、/en で日本語だけの中身には「Japanese only」）。プロフィールだけは例外で、注記もラベルも出さず、項目単位の代替表示だけで出す |
| 項目単位の代替表示 | 「言語あり」の中身でも、個々の項目（概要・所属・場所・肩書き・自己紹介など）が表示中の言語で空なら、その項目だけもう片方の言語の値を出す（注記は出さない）。どちらの言語も空なら、その項目ごと出さない。プロフィールは名前も含めて、この項目単位の代替表示だけで出す（プロフィールの「言語あり」の判定は、管理画面の言語タブの印にだけ使う） |
| 詳細本文だけ片方の言語 | 作品・プロジェクトで、タイトルは日英あるが詳細本文が片方の言語だけのとき、トップのカードには言語ラベルを付けない。詳細ページでは、もう片方の言語の本文を出して注記する（6.2.3） |
| UIの文言 | ボタン・見出し・注記などの固定文言は、日英の辞書で持つ。主な対訳は次の表 |
| 日付の表記 | 公開側の日本語: `2026年9月`、`2026年9月12日`、期間は `2024年4月 – 現在`。公開側の英語: `Sep 2026`、`Sep 12, 2026`、期間は `Apr 2024 – Present`。管理側: `2026/09/12`（年月だけの項目は `2026/09`） |
| タイムゾーン | 日付と日時の表示は、すべて日本時間（Asia/Tokyo）で行う |
| ブラウザの言語の判定 | ブラウザが最優先にしている言語が日本語（`ja` で始まる）なら日本語とする |
| 選んだ言語の覚え方 | ルート `/` の振り分けに使えるよう、Cookie に覚える |
| ページの言語の宣言 | ページの言語（`lang`）はURLの言語にする。もう片方の言語の本文を出している部分には、その部分の言語を指定する。各ページに、もう片方の言語のURLを代替ページとして示す |

主な固定文言の対訳:

| 日本語 | 英語 |
|---|---|
| プロフィール | Profile |
| 経歴 | Career |
| 職歴 ／ 学歴 | Work ／ Education |
| プロジェクト | Projects |
| 作品 | Works |
| 使用技術 | Tech Stack |
| ブログ | Blog |
| コーディング記録 | Coding Log |
| 学習ログ ／ コード断片 ／ 問題を解いた記録 ／ 技術メモ | Learning Log ／ Snippet ／ Problem Solving ／ Tech Memo |
| 現在 | Present |
| 続きを読む ／ 閉じる | Read more ／ Close |
| 英語のみ（/ja で英語だけの中身に出す） | Japanese only（/en で日本語だけの中身に出す） |
| サイトを見る | Visit site |

## 2. ユーザーロールとフロー

### 2.1 ロール定義

| ロール | 概要 | 主な操作 |
|---|---|---|
| 訪問者 | 採用担当・リクルーター、フリーランスの依頼主、エンジニア仲間など、サイトを見に来る人。ログインしない | 公開側の全画面の閲覧。セクション内ページング、詳細ページの閲覧、外部リンク・GitHubを開く、言語とテーマの切り替え |
| 管理者 | サイトの持ち主（自分）1人。GitHubアカウントでCMSにログインする | 経歴・作品・プロジェクト・ブログ・コーディング記録の作成・編集・下書き保存・公開・非公開化・削除。プロフィールの編集（1件だけで、下書き・削除はない）。使用技術の作成・編集・削除（下書き・公開はなく、トップに出すかを選ぶ）。並べ替え、画像のアップロード |

### 2.2 フロー全体像

```
訪問者（コアフロー「何者かつかみ、作品で確かめる」）:
  トップを開く → プロフィールと経歴で要点をつかむ
  → 同じページの作品欄・プロジェクト欄をセクション内でページングして見る
  → 作品詳細／プロジェクト詳細（背景・工夫・使用技術・画像）
  → 外部リンクやGitHubで実物を確かめる（別タブ）
  ※ 詳細のない作品・プロジェクトは、トップのカードから外部リンク・GitHubへ直接進む

訪問者（人となりを知る）:
  トップのブログ欄／コーディング記録欄をページングして見る → ブログ記事／コーディング記録詳細を読む → トップの該当セクションへ戻る

管理者（書いて公開する）:
  管理画面のURLを開く → GitHubでログイン → ダッシュボード
  → 各管理画面の一覧 → 新規作成または編集 → 下書き保存 → プレビューで確認 → 公開
  → 公開サイトで確認
```

| # | 画面名 | URL例 | 目的 | レイアウト | 認証 | 説明 |
|---|---|---|---|---|---|---|

| A6 | プロジェクト管理 | `/admin/projects`、`/admin/projects/{id}` | プロジェクトを更新する | 一覧: L4、編集: L5 | 必要 | 一覧（表示順の並べ替え）と編集（詳細本文・画像を含む） |
| A7 | 使用技術管理 | `/admin/stacks`、`/admin/stacks/{id}` | 技術スタックを更新する | 一覧: L4、編集: L6 | 必要 | 一覧（表示順の並べ替え）と編集（名前・アイコン・リンク・トップに表示するか） |
| A8 | ブログ管理 | `/admin/blog`、`/admin/blog/{id}` | 記事を書いて公開する | 一覧: L4、編集: L5 | 必要 | 一覧（公開日の新しい順、状態で絞り込み）と、Markdownエディタ・プレビュー・公開 |
| A9 | コーディング記録管理 | `/admin/coding`、`/admin/coding/{id}` | 記録を書いて公開する | 一覧: L4、編集: L5 | 必要 | 一覧（公開日の新しい順、状態・種類で絞り込み）と、Markdownエディタ・プレビュー・公開 |

- 新規作成は、各一覧ビューの「新規作成」から、空の編集ビュー（URL例: `/admin/works/new`）を開く。
- 管理画面のサイドメニューの並びは、公開側のセクションの並びに合わせる: ダッシュボード、プロフィール、経歴、プロジェクト、作品、使用技術、ブログ、コーディング記録。画面IDの番号順とは違う。
- 公開サイトには、管理画面への入口を置かない。管理画面はURLを直接開いて入る。
- 管理画面は検索エンジンに載せない（クロールさせない）。

## 4. デザインシステム

### 4.1 レイアウトパターン定義

| パターン | 名前 | 使う場面 | 構造 |
|---|---|---|---|
| L1 | シングルカラム・ロングページ | 1ページで全体を伝える画面 | 上部に固定ヘッダー、その下に読みやすい幅の1列で、セクションを縦に積む。画面幅が広くても1列のまま中央に置く。セクションごとにページングできる |
| L2 | 記事カラム | 1つの中身に集中して読ませる画面 | L1と同じヘッダーと、同じ幅の1列。上から「戻るリンク → タイトルとメタ情報 → 画像 → 本文 → 前後のナビ」の順 |
| L3 | 中央カード | 1つの操作だけをさせる画面 | 画面中央に小さなカードを1枚置く。ヘッダーやメニューはない |
| L4 | サイドメニュー＋一覧 | 管理画面で、たくさんの中身を見渡して選ぶ画面 | 左に固定のサイドメニュー、右に上部の操作バー（新規作成・絞り込みなど）と、テーブルや件数カードなどの一覧 |
| L5 | サイドメニュー＋2ペイン編集 | 管理画面で、長い本文を書いて確かめる画面 | 左にサイドメニュー、右の上部に操作バーと基本項目、その下を左右に分けて「Markdownエディタ ／ プレビュー」 |
| L6 | サイドメニュー＋フォーム | 管理画面で、短い項目を入力する画面 | 左にサイドメニュー、右に1列のフォーム。Markdownの欄は、ボタンで入力とプレビューを切り替える |

L4〜L6 のサイドメニューは共通で、上から「メニュー項目（3.3 末尾の並び）」、下部に「ログイン中のGitHubユーザー名（@で始まる表示）」「テーマ切り替え」「ログアウト」を置く。

### 4.2 画面 × レイアウト マッピング

| # | 画面 | パターン | スクロール | 根拠 |
|---|---|---|---|---|
| C1 | 見つからないページ | L2 | なし | 公開側の画面と同じヘッダーを出し、迷ったまま離脱させない |
| C2 | エラー | L2 | なし | C1と同じ。ヘッダーから他のセクションへも移れる |
| P1 | トップ | L1 | 縦に長い（ページ全体） | 「1ページで伝わる」原則。セクションの続きはページングで見るので、ページの長さは件数が増えても一定に保たれる |
| P2 | 作品詳細 | L2 | 縦（本文の長さ次第） | 1つの作品の背景と工夫を集中して読ませる |
| P3 | プロジェクト詳細 | L2 | 縦（本文の長さ次第） | P2と同じ |
| P4 | ブログ記事 | L2 | 縦（本文の長さ次第） | 長文を読みやすい幅で読ませる |
| P5 | コーディング記録詳細 | L2 | 縦（本文の長さ次第） | P4と同じ。コードブロックが読みやすいこと |
| A1 | ログイン | L3 | なし | 操作はGitHubでログインの1つだけ |
| A2 | ダッシュボード | L4 | 必要に応じて縦 | 全種類の状況を見渡し、次の作業を選ぶ |
| A3 | プロフィール編集 | L6 | 縦 | 短い項目が中心で、1件だけを編集する |
| A4 | 経歴管理 | 一覧: L4 ／ 編集: L6 | 縦 | 一覧で見渡し、編集は短い項目が中心 |
| A5 | 作品管理 | 一覧: L4 ／ 編集: L5 | 縦 | 詳細本文を書きながらプレビューで確かめる |
| A6 | プロジェクト管理 | 一覧: L4 ／ 編集: L5 | 縦 | A5と同じ |
| A7 | 使用技術管理 | 一覧: L4 ／ 編集: L6 | 縦 | 一覧で並べ替え、編集は短い項目だけ |

### 4.3 レスポンシブ方針

| ブレイクポイント | 幅 | 公開側（L1・L2） | 管理側（L3〜L6） |
|---|---|---|---|
| デスクトップ | ≥1024px | 1列のまま中央に置く。ヘッダーにメニューを横並びで出す。ページングは ◀ ▶ ボタン（キーボードの ← → も可） | サイドメニューを常に表示。L5はエディタとプレビューを左右に並べる |
| タブレット | 768〜1023px | 1列。ヘッダーのメニューは横並びのまま（入りきらなければメニューボタンにまとめる）。ページングはボタンとスワイプの両方 | サイドメニューはアイコンだけに縮める。L5は左右に並べたまま |

### 4.4 ビジュアルデザイン方針

具体的な値（色コード・フォント名・サイズ・余白）は、Phase 3 で `docs/06_design-tokens.json` として決める。

| 項目 | 方針 |
|---|---|
| トーン&ムード | ミニマム。装飾は最小限にして、あとから変更できるようにしておく。見た目はすべてデザイントークン経由で指定し、コンポーネントに色や余白の値を直接書かない。トーンを変えるときはトークンの差し替えで済むようにする |
| カラーの方向性 | モノトーン（白・黒・グレー）を基調に、アクセント1色。アクセントは、リンク・ボタン・ページングの現在位置など、操作できる場所だけに使う。アクセントの色相は Phase 3 で決める。ダークモードでは同じ色相のまま、読みやすさ（コントラスト）を保つように明るさだけ変える |
| タイポグラフィの方向性 | 和文はゴシック体、英文はサンセリフ体。コードと日付・数値は等幅を使う。見出しと本文の差は、サイズと太さだけでつける |
| ライト/ダークモード | 両対応。初期状態はOSの設定に合わせる。切り替え（OSに合わせる／ライト／ダーク）は、公開側はヘッダー、管理側はサイドメニューの下部に置き、選んだ設定は覚えておく。ログイン画面（L3）には置かず、覚えている設定かOSの設定に従う |
| 情報密度 | 公開側はゆったり（余白を広めにとって読みやすく）。管理側は高密度（一覧性と操作の速さを優先） |
| 画像 | サムネイルは同じ縦横比で切り抜いて揃える（比率は Phase 3 でトークンとして決める）。画像がない中身は、画像の場所を空けずに詰める。代替テキストは、サムネイルはその中身のタイトル、技術アイコンは表示名、写真は名前、本文中の画像は Markdown に書いた代替テキストを使う |
| 動き | ページングの切り替えは横にスライドする短いアニメーションだけにする。OSで「視差効果を減らす」が有効なら、アニメーションなしで切り替える |


| 項目 | 仕様 |
|---|---|
| 1ページの件数 | 縦に5件。PCでもスマホでも1列で、5件ずつ |

| 並び順 | 経歴: 開始日の新しい順。プロジェクト・作品: 管理画面で決めた表示順。ブログ・コーディング記録: 公開日の新しい順 |

#### 6.1.4 各セクションの表示内容

| セクション | 1件の表示 | 押したとき | ページング |
|---|---|---|---|
| プロフィール | 写真（任意）、名前、肩書き（任意）、自己紹介（Markdown）、SNSリンクのアイコン（`other` は汎用のリンクアイコンと表示名） | SNSアイコンは別タブで開く | なし |
| 経歴 | 期間（`2024年4月 – 現在`）、種類ラベル（職歴／学歴）、タイトル（役職・学位など）、所属、場所（任意）、内容（Markdown、2行まで）、言語ラベル（表示中の言語で「言語あり」でないとき。1.4） | 内容が2行を超えるときは「続きを読む」で、その場に全文を広げる（ページは移らない）。もう一度押すと閉じる | あり |
| プロジェクト | サムネイル（設定したものだけ）、タイトル、期間、概要（2行まで）、使用技術のアイコン（技術の表示順で最大6個、超えた分は「+N」）、言語ラベル（表示中の言語で「言語あり」でないとき。1.4） | 詳細本文あり → プロジェクト詳細（P3）へ。なし・外部リンクあり → 外部リンクを別タブで開く。どちらもなし → 押せない | あり |
| 作品 | サムネイル（設定したものだけ）、タイトル、概要（2行まで）、使用技術のアイコン（技術の表示順で最大6個、超えた分は「+N」）、外部リンク・GitHubのアイコン、言語ラベル（表示中の言語で「言語あり」でないとき。1.4） | カード本体: 詳細本文あり → 作品詳細（P2）へ。なし → 外部リンク、それもなければGitHubを別タブで開く。どれもなし → 押せない。外部リンク・GitHubのアイコンは、いつでも直接その先を別タブで開く | あり |
| 使用技術 | アイコンと表示名のチップ。「トップに表示する」にした技術を、管理画面で決めた表示順で全件並べる（折り返す）。アイコンがない・読み込めない技術は、表示名の頭文字の丸で代わりにする（カードのアイコン列でも同じ） | リンクがあれば公式サイトなどを別タブで開く | なし |
| ブログ | 公開日、タイトル、抜粋（2行まで。作り方は表の下）、サムネイル（設定したものだけ）、言語ラベル（表示中の言語で「言語あり」でないとき。1.4） | ブログ記事（P4）へ | あり |

- 表示するのは公開中の中身だけ。下書きは出さない。

| GitHub側でキャンセル | 「ログインがキャンセルされました」と出す。ボタンはそのまま押せる |
| 通信エラー | 「ログインできませんでした。もう一度お試しください」と出す |
| ログイン済みで開いた | ダッシュボードへリダイレクトする |

ログアウト: サイドメニューの「ログアウト」を押すと、ログインを終えてログイン画面へ移し、「ログアウトしました」と出す。

ログインの有効期限が切れたまま管理画面を操作したら（どの管理画面からでも）、ログイン画面へ移す。ログインし直したら、元の画面へ戻す。編集中の内容がある場合は、移る前に「ログインの有効期限が切れました。入力中の内容はこのブラウザに一時保存してあります」と出す。ログイン後に同じ編集ビュー（新規作成の途中なら空の編集ビュー）を開いたら、「一時保存した内容があります［復元する］［破棄する］」を出す。保存に成功するか破棄したら、一時保存を消す。

| 公開する | 入力を保存して公開する。ブログ・コーディング記録で公開日が空なら、公開日を今の日時にする |
| 更新する | 公開中のものを編集しているときに出す。保存すると公開サイトにも反映される。ブログ・コーディング記録では、タイトルか本文（どちらかの言語）が変わっていれば、更新日（`content_updated_at`）を今の日時にする。非公開のあいだの変更では、更新日を変えない |

#### 6.7.2 画面ごとの入力項目

| 画面 | 言語ごとの項目（日英） | 共通の項目 |
|---|---|---|
| A3 プロフィール編集 | 名前、肩書き、自己紹介（Markdown） | 写真、SNSリンク（サービスを選んでURLを入れる。`other` を選んだときは表示名も入れる。追加・削除・ドラッグで並べ替え） |
| A4 経歴管理 | タイトル、所属、場所、内容（Markdown） | 種類（職歴／学歴。初期値は職歴）、開始年月、終了年月（空なら「現在」） |
| A5 作品管理 | タイトル、概要、詳細本文（Markdown） | スラッグ、外部リンク、GitHub、使用技術（追加・削除・ドラッグで並べ替え。並びがカードに出る順になる）、サムネイル |
| A6 プロジェクト管理 | タイトル、概要、詳細本文（Markdown） | スラッグ、開始年月、終了年月（空なら「現在」）、外部リンク、使用技術（A5と同じ）、サムネイル |
| A7 使用技術管理 | なし（技術名は固有名詞なので日英共通） | 識別名、表示名、アイコン画像、リンク、トップに表示するか |

| A9 コーディング記録管理 | タイトル、本文（Markdown） | スラッグ、種類（学習ログ／コード断片／問題を解いた記録／技術メモ。初期値は学習ログ）、参考リンク、サムネイル、公開日（公開後に変えられる） |

- A3 プロフィール編集は1件だけなので、「保存」ボタンだけを置く（下書き・公開・削除はない）。保存するとすぐ公開サイトに反映される。

- スラッグのルール（作品・プロジェクト・ブログ・コーディング記録）:
  - 形式は半角の英小文字・数字・ハイフンだけ。
  - 自動で作る: 英語のタイトルから作る。同じ種類の中で重複するときは、末尾に `-2`、`-3` … を付ける。英語のタイトルがない、または変換して空になるときは、スラッグを空にする。英語のタイトルがなければ空のままで、公開するときに入力を求める。
  - 自動で追従する条件: 今のスラッグが「今の英語のタイトルから作った値」と同じで、かつ公開したことがないあいだは、英語のタイトルを変えるとスラッグも変わる。手で別の値に直したら、それ以降は追従しない（状態を持つカラムは要らない）。
  - 「公開したことがある」の判定: 作品・プロジェクトは `first_published_at` が、ブログ・コーディング記録は `published_at` が入っていること。
  - 公開したことがあるもののスラッグを変えたら、欄の下に「今のURLは見られなくなります」と出し、保存するときにも確認ダイアログを出す。

## 7. データモデル

論理設計。Phase 3 でORMのスキーマに変換し、所有権は System Design Doc に移る。

### 共通の約束

- すべてのテーブルに `id`（UUID、主キー）、`created_at`、`updated_at` を持たせる（以下の表では省略）。
- 日英を持つテキストは、`_ja` と `_en` の2つのカラムに分ける。どちらも空を許し、「言語あり」の判定（1.4）は各テーブルの備考のとおり。
- 公開状態 `status` は `draft`（下書き）か `published`（公開）。公開側には `published` だけを出す。
- 「必須」列の ✓ は、いつでも必須（DBの制約にする）。「公開時」は、下書きでは空を許し、公開するとき（`status` を `published` にするとき）に必須とする（6.7.3）。
- 表示順 `sort_order` は小さいほど先。新規作成したときは、作品・プロジェクトは先頭、使用技術・SNSリンクは末尾に入れる（6.7.1）。
- 画像は、ストレージに置いたファイルのURLを持つ。本文中の画像は Markdown の中にURLとして入る。
- Markdown のカラムは、Markdown 記法のテキストをそのまま持つ。
