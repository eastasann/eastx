# Feature Design Doc — プライバシーのページを足し、CMS で編集する

> 原則: 1ユーザーストーリー = 1 Feature Design Doc
> 変更規模: 大（アクセス解析の FDD と同じ壁打ちで扱った。公開側の新しい画面 P6 と管理画面の新しい画面 A11、テーブル・API・公開側のサーバー関数が増える）
> 関連: `docs/features/20261010-1638_access-analytics.md`（このページで告知する計測）。本番にはこちらを先に出し、本文を書いてから解析を昇格する（ロールアウト計画）

## 背景と目的

アクセス解析（関連の FDD）を始めると、訪問者の閲覧と行動を記録することになる。Cookie を使わず、個人を識別する値も残さない設計なので、同意のバナーは出さない。ただ、何を集めて、どれだけ残し、誰を除くかは、訪問者が確かめられる場所に書いておく。持ち主はそのために、プライバシーのページを公開側に足すことを選んだ（2026-10-10）。

持ち主が決めたこと（2026-10-10）:

- 告知は、フッターから移るプライバシーのページ（公開側の新しい画面）で行う。
- 本文は CMS で編集する（コードの辞書には置かない）。デプロイなしで直せるようにする。
- 編集は新しい画面 A11（L6。A3 と同じ形）で行う。サイドメニューは「アクセス解析」の後。

## Goal / Non-Goal

### Goal

1. 公開側に P6 プライバシー（`/ja/privacy`・`/en/privacy`）を足す。本文は日英の Markdown で、design-spec 1.4 の言語の代替と注記に従う。タイトルの下に最終更新日（行の `updated_at` を Asia/Tokyo の日付で。日英で同じ日付）を出す。
2. P6 にページのタイトル・説明・canonical・hreflang を ADR-019 の規則で出す（詳細設計の「P6 のメタ」）。
3. 公開側の全画面（C1 を含む）のフッターに、P6 へのリンク（「プライバシー」／「Privacy」）を置く。行が無いあいだと、本文が日英とも空のあいだは、リンクを出さず、P6 は C1 になる。フッターの中身を読めなかった画面（C2・どのルートにも当たらない C1）はリンクを出さない。
4. 管理画面に A11 プライバシー（`/admin/privacy`。L6）を足し、日英の本文を編集して保存できる。保存するとすぐ公開サイトに出る（下書き・公開・削除は無い。A3 と同じ）。保存済みの本文があるときは、A11 から公開サイトの P6 を開ける。
5. A11 で、L6 の編集ビューの共通の振る舞いのうち次の6つが効く（design-spec 6.4・6.7）: 自動退避と復元の提案、Cmd/Ctrl+S での保存、保存の状態の表示、ボタンを押せない理由（保存中）、保存していない変更があるときの移動の確認、表示の切り替え（片方｜日英）。

### Non-Goal

- 本文の版の管理（過去の版を残す・比べる）。最終更新日だけを出す。
- 本文の雛形を自動で作ること（集める項目を解析の実装から生成する）。持ち主が書く。
- 利用規約・特定商取引法の表記など、ほかの固定ページ。足すときは、このテーブルを汎用のページにする設計を改めて行う。
- 同意のバナー・オプトアウトの切り替え（DNT・GPC に従うことで代える。関連の FDD）。

## 実装アプローチ

- テーブルは `profile` と同じ「1件だけ」の形にする（`singleton` カラムが常に1で一意）。理由: 持ち主は本文だけを持てばよく、ページの種類を増やす予定は無い（Non-Goal）。汎用の「固定ページ」のテーブルにすると、スラッグ・一覧・作成と削除が要り、1ページのためには重い。
- 公開の状態を持たない。A3 と同じく、保存したらすぐ公開サイトに出る。下書きが要らない理由: 本文が日英とも空のあいだは公開側に何も出ない（リンクも P6 も無い）ので、書き始めの状態が公開されることは無い。書き直しは、A11 のプレビューで確かめてから保存する。
- 本文は SDD 5.0 のとおり前後の空白を除き、空になれば `NULL` で保存する（空白と改行だけの本文は `NULL`）。
- 「ページがある」の判定は「行があり、本文が日英のどちらかにある（`NULL` でない）」（design-spec 1.4 の言語ありの判定と同じ考え方を本文に当てる）。`src/domain/languages.ts` に判定を足し、公開側（`getPrivacyPage`・`getSiteChrome`）と API（`languages`）で同じ関数を使う。
- 最終更新日は行の `updated_at` で、専用のカラムを持たない。A11 は変更が無いときに保存を送らない（design-spec 6.7.1 の Cmd/Ctrl+S とボタン）ので、日付が進むのは本文を変えて保存したときだけ。片方の言語だけを直しても、両方の言語のページの日付が進む（1つの文書として扱う）。
- 本文を消して空にもできる（保存できる）。空にすると、フッターのリンクが消え、P6 は C1 になる。
- 描画は既存の Markdown の描画（ADR-012）で行い、使用技術は渡さない（太字のアイコンは付けない）。描画の結果は ADR-011 の Cache API に、種類 `privacy` で入る。
- P6 は詳細ページと同じ L2 で出す。戻るリンクは出さない（P1 のセクションから来る画面ではなく、ヘッダーのドメイン名でトップへ戻れる。C1 と同じ）。前後のナビも無い。
- 採らなかった案:
  - 本文をコードの辞書に持つ: 計測の実装と本文を同じ PR で直せ、食い違いにくいが、持ち主が CMS での編集を選んだ。食い違いは、関連の FDD のロールアウト計画（計測を変えたら A11 で本文を直す）と runbook の定期メンテナンスで防ぐ。
  - A3 プロフィールに欄を足す: 画面とテーブルが増えないが、プロフィールと関係の無い中身が混ざる。
  - A10 の中に編集の入口を置く: メニューは増えないが、入口が見つけにくい。

## 詳細設計

### API変更

#### `GET /api/admin/privacy`

```json
// 200
{
  "id": "9c2e…",
  "ja": { "body": "## アクセスの集計\n…" },
  "en": { "body": "## Analytics\n…" },
  "languages": { "ja": true, "en": true },
  "updatedAt": "2026-10-10T03:12:45.000Z"
}
```

- `id` は A3（5.5）と同じく行の ID を返す（自動退避のキーに使う）。
- `languages` は本文があるか（言語タブの印。design-spec 6.7.1）。
- 行がまだ無いときは `NOT_FOUND`。A11 は空のフォームを出す（A3 と同じ）。

#### `PUT /api/admin/privacy`

```json
// リクエスト
{ "ja": { "body": "…" }, "en": { "body": null } }
// 200: GET と同じ形
```

- 行がなければ作る。A3（`src/api/router/profile.ts`）と同じく、`insert(privacyPage).values({ bodyJa, bodyEn }).onConflictDoUpdate({ target: privacyPage.singleton, set: { bodyJa, bodyEn, updatedAt: new Date() } })` の1文で行う（D1 に対話的なトランザクションが無いので、確かめてから書く形にしない。ADR-006）。`onConflictDoUpdate` では `$onUpdateFn` が効かないので `updatedAt` を明示して入れる（P6 の最終更新日がこの値）。応答は書いた後に読み直して作る。
- 本文は前後の空白を除き、空なら `NULL` にして保存する（SDD 5.0）。
- 本文は日英とも空でもよい（空にするとページが無くなる。上の実装アプローチ）。
- エラー: `INPUT_VALIDATION_FAILED`（本文が Markdown の上限 100,000字を超える）。

#### 公開側のサーバー関数（5.11）

```ts
type PrivacyPageView = {
  lang: Lang; meta: PageMeta
  body: LocalizedHtml           // body.lang !== lang なら、本文の上に注記（design-spec 1.4）
  updatedAt: string             // 最終更新日（行の updated_at）
}
type SiteChromeView = {
  socialLinks: …                // 今どおり
  hasPrivacyPage: boolean       // 本文が日英のどちらかにある。読めなかったときは false（5.11 に書く決まり）
}
```

| 関数 | 入力 | 出力 | 見つからないとき |
|---|---|---|---|
| `getPrivacyPage` | `{ lang }` | `PrivacyPageView` | 行が無い・本文が日英とも空 → `notFound()`（C1） |

`getSiteChrome` は今の SNS リンクの読み取りと同じ `db.batch()` で、`privacy_page` の本文があるかだけを読む（本文そのものは読まない。式は `select (body_ja is not null or body_en is not null) from privacy_page`。行が無ければ `false`）。この式は、本文が `NULL` に正規化されていること（PUT と下の CHECK）を前提にする。同じ batch に足すと、テーブルの無い DB ではフッター全体が読めなくなるが、デプロイはマイグレーションをコードより先に当て、失敗すればデプロイしない（`docs/04_deployment-procedure.md` 2章）ので、新しいコードがテーブルの無い DB に当たることは無い。

#### A11 プライバシー編集（L6）

```
┌──┬──────────────────────────────────────────┐
│≡ │ プライバシー  保存済み 14:32   [片方｜日英]   [保存] │ ← 固定
│▣ ├──────────────────────────────────────────┤
│◎ │ [日本語 ●][English ○]                      │

└──┴──────────────────────────────────────────┘
```

- 操作バー: 戻るリンクは無し（A3 と同じ）、題は「プライバシー」、状態の札は出さない、保存の状態、表示の切り替え（片方｜日英）、ボタンは「保存」だけ。
- 欄: 言語ごとに「本文」（Markdown。A3 の自己紹介と同じ入力とプレビューの切り替え）。
- 本文の下に、保存済みの本文が日英のどちらかにあるときだけ「公開サイトで見る ↗」（`/ja/privacy` を別タブ）を出す。
- 保存の後は今どおり「保存しました」を通知する。本文を日英とも空にして保存したときは「保存しました。本文が空なので、公開サイトにはページとリンクが出ません」を通知する。
- 自動退避の種類は `privacy`、キーは `eastx:backup:privacy:{id か new}`（A3 の `profile` と同じく、行の `id`。行がまだ無ければ `new`）。
- 誤りの欄の順: 本文（日本語）→ 本文（英語）。
- 行がまだ無いときは空のフォームを出し、初めて保存したときに作る（6.7.4。A3 と同じ）。

### データマイグレーション

スキーマ差分（`src/db/schema.ts`）:

```ts
// ---- privacy_page -----------------------------------------------------
/** プライバシーのページ。1件だけ。本文が日英とも空なら、公開側にページもリンクも出さない */
export const privacyPage = sqliteTable(
  'privacy_page',
  {
    id: id(),
    /** 常に1。一意制約で2件目を防ぐ */
    singleton: integer('singleton').notNull().default(1).unique(),
    bodyJa: text('body_ja'), // Markdown
    bodyEn: text('body_en'), // Markdown
    createdAt: createdAt(),
    updatedAt: updatedAt(),
  },
  (t) => [
    check('privacy_page_singleton', sql`${t.singleton} = 1`),
    // 空白だけの本文は API が NULL にする。「ページがある」の判定（is not null）の最後の守り
    check('privacy_page_body_ja', sql`${t.bodyJa} is null or trim(${t.bodyJa}) <> ''`),
    check('privacy_page_body_en', sql`${t.bodyEn} is null or trim(${t.bodyEn}) <> ''`),
  ],
)
```

1. 新しいテーブルを足すだけ。`make db-generate`（drizzle-kit 0.31.11）の出力が `CREATE TABLE` と一意インデックスだけであることを読んで確かめる（ADR-007）。
2. 既存のデータの移行は無い。本番・staging は行が無い状態で始まり、A11 の初めての保存で作られる。行が無いあいだは公開側にページもリンクも出ない。
3. 古いコードとの両立: 古いコードは新しいテーブルを読まないので、そのまま動く。
4. ロールバック: アプリを戻すと P6・A11・フッターのリンクが無くなり、テーブルと行は残る（前進のみ）。
5. シード: `scripts/seed/insert.ts` の消すテーブルの並びに `privacy_page` を足す（足さないと2回目の `make db-seed` が `singleton` の一意制約で落ちる）。`scripts/seed/data.test.ts` に「privacy_page は1件で、日英とも本文あり」の検査を足す。ローカルの `privacy_page` に、日英の本文（アクセスの集計の説明。集める項目・保持・除外を、関連の FDD の「個人情報」の段落に合わせて書く）を入れる。`make db-seed-empty` でも入れる。design-spec 8章に「privacy_page | 1 | 日英とも本文あり」を足す。言語の代替の確認は、E2E が A11 で英語の本文を空にして確かめる（シードで片方だけにはしない。フッターのリンクの確認を両方の言語で行うため）。

## テスト方針

| テスト種別 | 対象 |
|-----------|------|
| Unit | `src/domain/languages.ts` のプライバシーのページの「ページがある」と言語ありの判定（行が無い、日英とも `NULL`、片方だけ）。A11 のフォームの規則（自動退避の種類・誤りの欄の順・空の本文で保存したときの通知の文言） |
| Integration | `GET /api/admin/privacy`（行が無いと 404）、`PUT`（行が無ければ作る、2回目は更新して `updatedAt` が進む、日英とも空で保存できる、空白と改行だけの本文が `null` になる、100,000字を超えると 422）、未認証 401・管理者でないセッション 403。`getPrivacyPage`（行が無い・日英とも空で notFound、片方だけで代替と `body.lang`）。`getSiteChrome` の `hasPrivacyPage`（行が無い・空・片方だけ）。P6 のメタ（タイトル、片方だけのときの説明の言語、hreflang の3つ）。Markdown のキャッシュのキーの種類 |

## ロールアウト計画

1. 実装・`main` へのマージ・staging への昇格。staging で確かめること: マイグレーションの適用、行が無いあいだはフッターにリンクが無く /ja/privacy が C1、A11 で保存するとリンクと P6 が出る、空にすると消える。staging の本文は確かめた後に空に戻してよい。
2. 本番に昇格する。行が無いので、公開側の見た目は変わらない。
3. アクセス解析の FDD を本番に昇格する前に、本番の A11 で本文（集める項目・保持・除外。関連の FDD の「個人情報」の段落）を書いて保存する。フッターのリンクと P6 が出ることを確かめてから、アクセス解析を昇格する。
4. ロールバック: 昇格 PR の revert。行は残り、次に戻したときにそのまま出る。アクセス解析が本番にあるあいだは、先に解析を戻してから、このページを戻す（告知が消えて計測だけが残る時間を作らない）。

## 実装での差分

設計の判断は変えず、細部を次のとおりにした。

- 本文の CHECK: SQLite の `trim(X)` は半角スペースしか除かないので、上のスキーマ差分のままでは改行だけの本文が DB を通る（API は JS の `trim` で空とみなして `NULL` にする）。API を通さずに空白だけの本文が入ると、フッターは「本文がある」とみなしてリンクを出し、P6 は C1 になって食い違う。除く文字を JS の `trim` と同じ集合（ECMAScript の WhiteSpace と LineTerminator）にして `trim(X, char(9, 10, …, 65279))` で渡し、その集合が JS の `trim` と一致することを結合テストで確かめる。
- `getSiteChrome` の判定: 生の SQL の式（`body_ja is not null or body_en is not null`）ではなく、本文の有無だけを読む既存の部品（`bodyPresence`）で読み、`src/domain/languages.ts` の `hasPrivacyPage` で決めた。「公開側と API で同じ関数を使う」（実装アプローチ）をフッターでも満たすため。本文の全文を読まないこと、`NULL` への正規化を前提にすることは変わらない。
- 管理画面の範囲の表記: A10 がまだ無いので、「A2〜A11」ではなく「A2〜A9・A11」と書いた（SDD 5.2・7章、画面遷移図）。CMS API の新しい節はこの FDD が先に入ったので 5.12 になった。
- ソースドキュメントは上の表の行に加え、同じ事実を持つ箇所（design-spec 2.1・4.1 の L6・6.7 の操作バー・6.7.1 の Cmd/Ctrl+S・6.7.3、SDD 7章のルートガードの注記・10章）も合わせて直した。
