# Feature Design Doc — 公開サイトのデザイン刷新

> 原則: 1ユーザーストーリー = 1 Feature Design Doc
> 変更規模: 大（P1 トップの構成とヘッダー、design-spec 1.3・4章の原則が変わる）
> 関連: 管理画面の UX 改善は別の FDD で扱う。この FDD で変える共通のトークン（書体・本文の大きさ・リンクの色）は管理画面にも効くので、管理画面の FDD はこの FDD の完了を前提にする

## 背景と目的

今の公開サイトは、カード（枠線・サムネイル・2行の概要・技術アイコン）を縦に積み、固定ヘッダーにセクションメニューを置いている。これを、情報を絞った静かな見せ方に変える。目指す形は、狭い1列、小さめのグレーの本文、固有名詞だけを濃い色にする強調、`名前 ~ 短い説明 ……… 右寄せのメタ` という1行の行、細い区切り線、簡素なヘッダー。

ただし、詳細ページへ移らなくても作品・プロジェクトの中身（概要・サムネイル・使用技術）を見比べられることは残したい。そこで、作品・プロジェクトの行は経歴と同じく、左の ▸ でその場に概要・サムネイル・使用技術を広げられるようにする。

PRD との関係: V-2（ページを移らずに見比べる）、V-3（作品の詳細）、V-10（戻ったときのページ）、V-11（テーマ）、V-13（キーボードでのページング）は満たし続ける。スコープ外（PRD 6章・design-spec 9章）には踏み込まない。KPI の Lighthouse は、今の値（下の「テスト方針」）から PRD 5章の目標を割らないこと。

目指す形と今のサイトの違い（今のサイトは 2026-10-07 にデスクトップ幅 1424px で確認）:

| 観点 | 目指す形（この FDD で決めた値） | 今の eastasian |
|---|---|---|
| 列の幅 | 520px | 約560px |
| 本文 | 15px の Geist。自己紹介はグレーで、太字（固有名詞）とリンクだけ濃い色。太字の技術名には小さなアイコン | 16px の Inter、全文が同じ濃さ |
| セクション見出し | 小さなグレーのラベルと細い区切り線 | 大きめの太字 |
| 項目 | 1行の行。経歴・作品・プロジェクトは ▸ で広げると中身を出す | 複数行のブロックとカード |
| ヘッダー | サイト名・JA｜EN・テーマ。固定しない | 固定。セクションメニュー・JA/EN・テーマ |
| ページング | セクションごとに10件 | セクションごとに5件 |

## Goal / Non-Goal

### Goal

1. P1 の項目を1行の行にし、セクション見出しを小さなラベルと細い区切り線にする（「UI変更」の図と表のとおり）。
2. 作品・プロジェクトの行の左に ▸ を置き、押すとその場でサムネイル・概要・使用技術（プロジェクトは期間も）を広げる。行のほかの部分は今と同じく行き先（詳細ページ・外部リンク）へ移る。
3. 経歴を1行の行にし、行の左の ▸ を押すとその場で種類・場所・内容を広げる（今の「続きを読む」を置き換える）。
4. セクション内ページングを1ページ10件にする。
5. P1 のブログ・コーディング記録の行から、抜粋とサムネイルを外す。`getTopPage` はそれらを返さず、本文の先頭も読まない。
6. ヘッダーを固定しない簡素な形（サイト名・JA｜EN・テーマ）にし、セクションメニューをやめる。`getSiteChrome` の `sections` をやめる。
7. 自己紹介の Markdown で、太字の語が登録済みの使用技術と一致したら、前にアイコンを付ける。公開側の P1 と、管理画面の A3 のプレビューの両方で同じに描く。
8. トークンを「UI変更」の表のとおりに変える。共通の値（欧文の書体を Geist、本文の `typography.body` を 15px、本文中のリンクを濃い色と下線）は、管理画面にも同じに効く。公開側の列の幅は、公開側だけが使う新しいトークン `size.site-column`（520px）で持つ。
9. 詳細ページ（P2〜P5）と C1・C2 を、P1 と同じヘッダー・列の幅・リンクの色にする。
10. デモデータを、作品のページングと自己紹介のアイコンを確かめられる形にする（「データマイグレーション」）。

### Non-Goal

- 管理画面のレイアウトと操作の変更（別の FDD）。この FDD で管理画面に起きる変化は、Goal 7 の A3 のプレビューと、Goal 8 の共通の値（書体・`typography.body`・本文中のリンクの色）だけ。管理画面の見出し（`heading-1`・`heading-2`）、フォームとダイアログとトーストの幅（`size.content`）、`ui`・`body-sm`・`label` の大きさは変えない。
- ブログ・コーディング記録・作品などの本文での技術アイコンの差し込み（自己紹介だけに限る）。
- 初めのテーマの変更（今どおり OS に合わせる。V-11）。
- 新しいページ（写真のギャラリーなど）や、問い合わせの導線（面談の予約・メール）の追加。
- DB スキーマと CMS API（`/api/admin/*`）のコントラクトの変更。
- 動きの追加（design-spec 4.4 の「動き」の範囲は変えない）。

## 実装アプローチ

### 行を広げる（経歴・作品・プロジェクト）

- 行の左に ▸ のボタン（`aria-expanded`・`aria-controls`。読み上げ名は行の名前）を置き、押すとその場で広げる・閉じる。広げると ▾ にする。
- 経歴は行き先が無いので、▸ のほかの部分は押しても何も起きない。作品・プロジェクトは、▸ のほかの部分は今と同じく行き先へ移る（行全体のリンク。外部リンク・GitHub のアイコンは直接その先へ）。▸ は行のリンクより上に重ねる。
- 広げても出すものが無い作品（サムネイル・概要・使用技術のどれも無い）には ▸ を出さず、その幅だけ空けて名前の位置を揃える。プロジェクトは期間を必ず持つので、いつも出す。
- 複数の行を同時に開ける。ページを切り替えたら閉じる。言語の切り替え・詳細ページから戻ったときは閉じた状態で描く（広げた行は覚えない）。
- 採らなかった案:
  - セクションごとの「一覧｜詳しく」の切り替え（Cookie に覚えて SSR で反映）: 持ち主が経歴と同じトグルの形を選んだ。行ごとに広げれば、見比べたい項目だけを開ける。
  - 行全体を押して広げ、広げた中に「詳細を見る」を置く: 詳細ページへ移るのに1回多く押すことになる。

### ページングと展開の関係

- 1ページは10件。`page-memory.ts`（戻ったときのページ番号）と、戻るリンクの `itemId` の仕組みは変えない。
- 10件以下のセクションは、今と同じくページ表示とボタンを出さない。
- セクションの高さ: 閉じた状態で一番高いページに揃える。行を広げた分は伸ばす（今の「続きを読む」と同じ）。
- キーボード: ▸ はボタンなので Enter・Space で広げる。ページングの ← → は、今どおりページングの部品にフォーカスがあるときだけ。

### 自己紹介の技術アイコン

- `src/markdown/` に、rehype のプラグインを足す。対象は、子が1つのテキストだけの `strong`。テキストの前後の空白を除き、使用技術の `displayName` か `key` と、大文字小文字を区別せずに（`toLowerCase()` で）完全一致で照合する。`displayName` は日英共通（SDD 6.3）なので、言語ごとの照合は要らない。複数の使用技術に一致したら、`key` の昇順で最初のものを使う。
- 一致したら、`strong` の直前にアイコンを入れる。`iconUrl` があれば `<img src={iconUrl} alt="" width height>`（隣の `strong` に表示名があるので、読み上げが重ならないよう装飾として扱う）、なければ使用技術のセクションと同じ頭文字の丸（`aria-hidden`）。
- 位置は、rehype-sanitize の後、見出しのレベルと外部リンクの処理の前（ADR-012）。サニタイズのスキーマは広げない。`src` は DB の `iconUrl`（CHECK 制約 `stack_icon_url` で `/media/` 始まり）だけ。描画結果は UI の言語に依らない（ADR-012 の方針のまま）。
- `renderMarkdown` のオプション `stacks?: { key: string; displayName: string; iconUrl: string | null }[]` を渡したときだけ動く。渡すのは自己紹介の描画（公開側の `getTopPage` と A3 のプレビュー）だけ。照合に使うのは、「トップに表示する」に関わらず全使用技術。
- Cache API のキー（ADR-011）: `stacks` を渡した描画だけ、キーの末尾にセグメント `/s-{版}` を足す（`.../{updated_at}/s-3f9a1c0b`）。渡さない描画は今のキーのまま（末尾に `/` を足さない）。版は、使用技術を `key` の昇順に並べ、各項目を `{key}\u0000{displayName}\u0000{iconUrl ?? ''}`、項目どうしを `\n` で連ねた文字列の SHA-256 の先頭8桁（16進）。並べ替え（`sort_order`）と「トップに表示する」の変更では版は変わらない。追加・削除・表示名・識別名・アイコンの変更で変わる。
- A3 のプレビューはブラウザで描くので、Cache API を使わない（今と同じ）。
- 採らなかった案: 専用の記法（`:stack[react]`）は、書くときに識別名を覚える必要があり、未知の識別名の扱いも要る。文中の語の自動の照合は、「Go」「Bun」などを誤って拾う。

### トークン

- 共通の値（書体・`typography.body`・本文中のリンクの色）は変え、管理画面にも同じに効かせる（持ち主の決定）。管理画面が使う `typography.ui`・`body-sm`・`label` の大きさは変えないので、管理画面の情報密度（design-spec 4.4）は保たれる。
- 公開側の列の幅は、共通の `size.content`（720px）を変えずに、新しい `size.site-column`（520px）を足して使う。`size.content` は管理画面のフォーム（`src/admin/layouts.tsx`）、ダイアログ（`src/ui/dialog.tsx`）、トースト（`src/ui/toast.tsx`）も使っていて、520px にすると管理画面のフォームとダイアログが狭くなるため。
- 見出しは `heading-1`・`heading-2`・`display` の値を変えない（`heading-1` は管理画面の各画面の題、`heading-2` はダッシュボードと A1 と本文の `##` が使う）。P1 の見た目は、使うトークンを替えて作る: セクション見出しは新しい `section-label`、プロフィールの名前は `display` から `heading-2` へ。

### デプロイの前後での版の食い違い

- `SiteChromeView` から `sections` を、`TopPageView` から `excerpt`・`thumbnailUrl` を外すので、デプロイの前に開いたままのタブ（古い JS）が、画面の移動で新しい Worker のサーバー関数を呼ぶと、描画に失敗しうる。ロールバックのときは向きが逆になる。
- これは今のどのデプロイでも起きうることで、失敗はルートの `errorComponent` の C2（「再読み込み」ボタン）で受け、再読み込みで新しい版になって直る。この FDD では古い形を返し続ける互換の層は作らない（作ると、後で消す作業が残るため）。
- staging で、デプロイの前に開いたタブから画面を移り、C2 になって再読み込みで直ること（白い画面や壊れた描画にならないこと）を確かめる（「ロールアウト計画」2）。

## 詳細設計

### API変更

CMS API（`/api/admin/*`）の変更はない。A3 のプレビューは、今ある `GET /api/admin/stacks` を TanStack Query で読む。

公開側のサーバー関数（SDD 5.11）:

```ts
type TopPageView = {
  // ...（変わらない項目は省略）
  profile: null | {
    name: LocalizedText | null
    headline: LocalizedText | null
    bio: LocalizedHtml | null          // 太字と一致した使用技術のアイコン入り
    avatarUrl: string | null
    socialLinks: { service: SocialService; url: string; label: string | null }[]
  }
  blogPosts: {
    id: string; slug: string; publishedAt: string; title: LocalizedText; availability: Availability
  }[]                                  // excerpt・thumbnailUrl を外す
  codingLogs: {
    id: string; slug: string; kind: CodingLogKind; publishedAt: string; title: LocalizedText
    availability: Availability
  }[]                                  // excerpt・thumbnailUrl を外す
}

type SiteChromeView = {
  socialLinks: { service: SocialService; url: string; label: string | null }[]  // sections を外す
}
```

- `getTopPage` は、自己紹介の描画のために使用技術の全件（`key`・`displayName`・`iconUrl`）を同じ `db.batch()` で読む。ブログ・コーディング記録は本文を読まない。

## ロールアウト計画

1. 実装を PR で `main` に入れる。`make lint`・`make typecheck`・`make test`・`make e2e` が通ること。
2. staging で確かめる準備: デプロイの前に、staging の公開サイトのトップを1つのタブで開いたままにしておく（版の食い違いの確認用）。staging の管理画面で、自己紹介に技術名の太字を入れて保存する（staging のプロフィールはシードではないため。持ち主の作業）。
3. `make promote ENV=staging` で昇格 PR を作り、マージして staging に出す。確かめること:
   - P1 が 200 で返り、Geist の woff2 が 200 で返る。
   - 自己紹介の HTML に、太字にした技術のアイコンの `img` が入る（描画の版が上がり、古いキャッシュの結果ではない）。
   - staging の管理画面で、その技術の表示名かアイコンを変える（プロフィールは保存しない）と、P1 の自己紹介のアイコンが変わる（キーの使用技術の版が効いている）。確かめたら元に戻す。
   - 2 で開いたままのタブで画面を移り、C2 が出て「再読み込み」で新しい版の画面になる（白い画面や崩れた描画にならない）。
   - staging の作品が10件以下なら、作品のページングは確かめない（E2E で確かめている）。
4. 同じ SHA を `make promote ENV=production` で本番に出す（`docs/04_deployment-procedure.md`）。
5. デプロイの直後: 本番の P1 が 200、Geist の woff2 が 200、Sentry に新しいエラーが無いこと。`RENDER_VERSION` を上げたので、Markdown の描画結果のキャッシュはすべて外れる。P1 と、本文の長い P4 を一度ずつ開いて温める（外れたままでも、初回の描画が遅いだけで表示は正しい）。
6. デプロイの7日後: Sentry の Web Vitals で、P1 の TTFB と P1〜P5 の LCP の p75（日本から）を、デプロイ前の7日の p75 と比べる。PRD 5章と SDD 7章の目標（TTFB 500ms 以下、LCP 2.5秒以下）以内なら合格。外れたら原因を調べ、別の変更として直す。
7. 本番の自己紹介に、技術名の太字を管理画面から入れる（任意。持ち主の作業）。
8. 戻すときは昇格 PR を revert する。DB に変更がないので、それだけで戻る。

## 実装中に決めたこと

### 設計の変更（持ち主と合意）

- 作品・プロジェクトの「一覧｜詳しく」の切り替え（セクションごとに Cookie `eastx-view` に覚え、SSR で反映）をやめ、経歴と同じく行ごとに ▸ で広げる形にする。▸ のほかの部分は今と同じく行き先へ移る。経歴も ▸ だけで広げる形にそろえる。本文の Goal 2・3、「実装アプローチ」「UI変更」「テスト方針」はこの形に書き換えてある。Cookie・Ark UI の SegmentGroup・辞書の `view` は使わない。
- 言語の切り替えで「トップでは見ていたセクションのスクロール位置を保つ」（design-spec 1.4、SDD 4.1）をやめる。ヘッダーを固定しないので、JA｜EN はページの一番上でしか押せず、押した時点で画面の上端にかかっているセクションが無いため、この仕組みは働かない。切り替えた先はページの一番上から始まる（押す前と同じ位置）。言語の切り替えで history state に `section` を渡す処理と、表示中のセクションを測る処理を消す。詳細ページの戻るリンクの `section`・`itemId` は残す。URL のハッシュも引き継がない（`/ja#works` から切り替えても、切り替えた先は一番上から始まる）。

### 細部の決定

- 書体: OGP の既定の画像と favicon（`scripts/og/generate.ts`）も Inter の woff2 を埋め込んでいたので、Geist に替えて作り直す（スクリプトの決まり「トークンを変えたら作り直してコミットする」）。
- トークン: 使われなくなる `size.avatar`（P1 の写真は `avatar-sm`）と `z-index.header`（ヘッダーを固定しない）を消す。本文中の技術アイコンと語の間に `space.inline-tight`（4px）を足す（今いちばん狭い `space.inline` の 8px は 15px の本文には広い）。使い道が変わった `size.header`・`size.thumbnail-card`・`typography.*` の説明を直す。
- 使用技術のチップ: 枠線のない形を `chip` のレシピのバリアント（`plain`）にする。レシピは管理画面（A5・A6）も使うので、レシピそのものは変えない。公開側のチップ（P1 と P2・P3）は同じ部品なので、P2・P3 のチップも枠線なしになる。
- 色: アクセントを「フォーカスの枠、ページングの現在位置、今の言語、ボタン」に限る方針に合わせ、ヘッダーの JA｜EN の選んでいない側とフッターの SNS リンクはグレー（ホバーで濃い色）にする。公開側のチップのリンクも、ホバーはアクセントにせず下線にする。
- 抜粋: 本文の先頭だけを読む処理がなくなるので、`EXCERPT_SOURCE_LENGTH` と、切った位置で閉じていないコードブロックを捨てる `dropUnclosedFence` を消す（全文なら、閉じていないフェンスは CommonMark でも文書の終わりまでコードになり、結果は変わらない）。
- 自己紹介の技術アイコン: `img` は `data-stack-icon` と `data-initial`（頭文字）を持ち、読み込めないときは `MarkdownBody` が頭文字の丸に置き換える（今の本文の画像の「背景色だけの枠」にはしない。design-spec 6.1.5）。
- A3: 使用技術の一覧を読めないときは、プロフィールを読めないときと同じ「読み込めませんでした（再試行）」を出す（アイコンなしのプレビューに黙って落とさない）。
- コードブロックの「コピー」ボタン: 列が 520px になり、ボタンがコードの1行目に重なりやすくなったので、コードブロックの上の余白を広げてその中に置く。
- ヘッダーを固定しないので、ハッシュへのスクロールの止まる位置を下げていた `scroll-padding-top` を消す。
- 言語の切り替えは同じルートのままパラメーターだけが変わり、部品が作り直されないので、ページングの部品がパスの変化を見て項目を作り直し、広げた行を閉じる。
- ▸ のボタンは、行の左の余白と名前との隙間も押せる範囲に含め、右側（名前・メタ・右の余白）は行き先へのリンクの範囲にする。行のどこを押しても「広げる」か「行き先へ移る」のどちらかになる（ホバーで地が変わるのに押しても何も起きない帯を作らない）。▸ の読み上げ名は行の名前（作品・プロジェクトはタイトル、経歴は `所属 ~ タイトル`）だけにし、概要や「別タブで開く」を含めない。
- `Menu` の `onClick`（消したセクションメニューだけが使っていた）を外す。管理画面の使用技術の欄のラベルの「並びがカードに出る順」を「並びがトップの行に出る順」にする。
- デモデータ: コアフローの E2E は前後のナビで移った先で「サイトを見る」を確かめる。レシピノートの前の作品（家計簿アプリ）に外部リンクを持たせる。
